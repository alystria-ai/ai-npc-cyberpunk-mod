# Latency pass, 2026-10-13: every hop from the player's last word to the first sound

> Groq was removed as a conversation provider by the user on 2026-10-14 (route, key handling, prompt shaping, scripts). The Groq parts below are history and describe code that no longer exists.

Latency here is the time from the player finishing a message (the Enter key, or the second press of the voice key; in person
or on the phone) to the companion being audible, or to the reply being visible for a phone text. This pass maps every hop on
every route, ranks them by milliseconds per turn times how often they happen, cuts the ones that do not collide with the
agents working on the voice, text-host and Local AI code, and writes the rest down as exact proposals.

**Status: the cuts are built and unit-tested; NOT yet seen in the game** (they need the mod files installed and a bridge
restart). The game was closed during the work and nothing was installed.

Sources: the live stage records in `runtime/bridge-latency.json` (seven turns, 2026-10-13 02:36 to 02:51 IST: five Mistral +
Voxtral turns with Judy, one incomplete, one Local AI + OmniVoice), `bridge.stderr.log` from the same session, the code, and
offline measurements on this machine (game closed, idle). The records were made before the knowledge cut of `401c444`, so
their `received` to `knowledge` step (20 to 137 ms) is now about 1 ms.

(2.8 to 3.5 s to sound without the 28 s outlier), that is 14 to 17 percent.

### 2.4 Convai (text and its cloud voice)

The bridge part is the same as 2.1 hops 1 to 5 and 13 to 14; the middle is Convai's own (its connection is warm after the
composer opens, `connectionWarm.warmMs` 1 ms in every record). The watcher and the Lua probe apply. Not measured live in this
pass: live Convai turns write to the user's memory.

### 2.5 OmniVoice (local GPU voice), any text route

The first phrase is synthesized whole, then its lip-sync is analysed, then the WAV is stored for the game, then the reply is
published. Live (Local AI + Omni, 4.56 s first phrase): `firstPcm` 69,723 ms, `published` 72,078 ms: **2,355 ms**, of which the
analysis is 1,955 ms (`lipAnalysisMs`) and storing 363 ms (`audioStoreMs`). A helper's investigation (section 4.6) found the
analysis is a pure-JavaScript convolution network (about 0.66 M multiply-adds per 10 ms of audio), 650 to 760 ms offline for the
same length and 2.6 times slower live (the game and Omni rendering phrase 2 at the same time), and the 363 ms is nearly all
serialized file writes. The kernel is now about 8 times faster (section 1), so the analysis should drop to about 0.25 s live
(2.6 times the offline 96 ms); the other proposals are in 4.6.

### 2.6 Group chat

Each speaker is a turn of 2.1 or 2.4; the next speaker is generated ahead while the current one speaks (`group-lookahead`), so
only the first speaker's latency is felt. Everything in 2.1 applies to that first speaker.

### 2.7 The game side, common to every route

- Lua to bridge: the plugin's worker writes at once (queued, atomic); the bridge saw it on its next poll (now: the watcher).
- Bridge to Lua: the plugin's worker polls `reply.json` (now 15 ms), Lua read it on the 0.1 s tick (now: a 30 ms revision probe
  while a reply is due). A channel unread for 3 s backs off to 500 ms; the first read after that returns the last copy and the
  next one is fresh, so the first tick of a new turn can miss one poll.
- Playback start, continuous voices (Pocket, Voxtral, Convai): the bridge publishes when it has validated PCM and text (it
  does not wait for 400 ms of audio); Lua starts the lease at once (`continuous-speech.lua`, `M.start` writes
  `continuous-control.json`); the bridge's pump reads the lease on its next iteration (40 ms sleep plus the iteration's work:
  renderer snapshot, face, state and face-file writes); the renderer starts when it has 400 ms buffered (`startupSeconds`) and
  the lease allows. In every live turn the 400 ms was already buffered at `published` (`initialBufferedSeconds` 0.1 to 0.4,
  `receivedSeconds` 0.4 to 0.8), so the buffer was not the wait; the round trip was.
- The Lip sync delay setting (150 ms, auto, Bluetooth) moves the heard position back; it is real device latency, not ours.
- Omni phrases play through Audioware from a WAV file after the lip-sync analysis (2.5).

## 4. Queued for the agents working in those files (exact proposals)

### 4.1 Voice key on a text route: stream the first sentence (voice path, text host)

**Status 2026-10-13 (`latency-queue`): built, unit-tested through the real `MicrophoneSession`, local speech channel and text host; not yet in the game.** `bridge/voice-key-stream.mjs` (`startVoiceKeyStream`). `prepareReply` in `bridge/convai-bridge.mjs` creates the `ReplyStream` for a local voice on a text route and starts `voiceStreamedReply` (the voice half of `respondStreamed`, now shared) at once; `onReply` hands the finished reply over (`finish`) and awaits what the voice returns; a failure or a cancel aborts the voice. The transcript reaches the first sentence's admission through `options.onTranscript` (`bridge/local-stt-capture.mjs`). Measured with `node scripts/Measure-TurnLatency.mjs --voice-key --runs 3` (real `MicrophoneSession`, local speech channel, text host, `ReplyStream`, `deliverPocketSpeech` and the headless muted renderer; simulated model and voice), whole reply first against first sentence first, `published` / `playbackObserved` in ms after the request: Mistral + Voxtral 2,572 / 2,808 to 2,093 / 2,346; Groq + Voxtral 2,659 / 2,943 to 2,252 / 2,541; local + Voxtral 3,883 / 4,201 to 2,722 / 2,985; local + Pocket 2,549 / 3,280 to 1,413 / 2,265. The harness' model writes 2.6 ms per character, so the cloud gain (0.4 to 0.46 s) is larger than the 0.17 to 0.45 s estimated from the live records.

`bridge/convai-bridge.mjs`, `const mic = new MicrophoneSession({... prepareReply, onReply})` (about line 1363): on a text route
the whole reply is written before `onReply` voices it. Proposal: in `prepareReply`, when `mistral.active && replyStreaming`
(and the voice is a Pocket-engine one), create the `ReplyStream` there and return `{stream}`; `finishVoice` already spreads its
options into the text host's `reply(config, options)` (`bridge/local-stt-capture.mjs` about line 204), so the stream is fed. Then
run the body of `respondStreamed` from `const head = await abortable(stream.headReady, signal)` onward, with `final` = the
`finishVoice` promise, from a hook that `prepareReply` starts (the head must be voiced before `finishVoice` resolves; today
`onReply` only runs after it). `onReply` then publishes the result it already has. Saves 0.17 to 0.45 s on Mistral and Groq,
about 1.2 s on the local AI, every voice-key turn on a text route. Test: a fake STT channel and a fake SSE text route, as
`bridge/reply-stream-tags.test.mjs` does for the typed route.

### 4.2 Wake the playback pump on the game's lease (voice path)

**Status 2026-10-13 (`latency-queue`): built, unit-tested.** `LocalPcmHost.play` takes `wake` (as the Convai host's `liveSpeech.wake` does); `ConvaiContinuousSpeech.options.wake` returns the lease latch only until the first lease is read (a wake on every 150 ms refresh would only add polls); `createWakeSignal` in `bridge/file-wake.mjs` (a fire nobody waited for is kept for the next wait) is fired by the directory watcher on `continuous-control.json`. Measured with the real `LocalPcmHost` and a fake renderer (40 leases at random points of the 40 ms cycle, two rounds): lease written to applied 24.9 and 23.9 ms mean before, 12.3 and 13.8 ms after. The floor is Windows' 15.6 ms timer granularity under the watcher's own 4 ms delay (`setTimeout(4)` fires after about 15 ms), so the real gain is about 11 ms, not the 20 to 40 ms estimated. The Convai host pump gets the same wake.

`bridge/local-pcm-host.mjs`, `play`, the pump loop: after `onFrame` it sleeps `pollMs` (40 ms) whatever happens. The game's lease
(`continuous-control.json`) is what releases the first sound, so the pump should run the moment Lua writes it. Proposal: give
`play` an optional `wake: () => Promise` (as the Convai host's `options.wake` already is) and race the 40 ms sleep against it;
in `bridge/convai-bridge.mjs` resolve that promise from a `watchFiles(runtime, {'continuous-control.json': ...})` watcher
(`bridge/file-wake.mjs`, already in the bridge) while a stream is waiting for admission. Saves about 20 to 40 ms on every
continuous reply. No game change.

### 4.3 Publish before the face write (voice path)

**Status 2026-10-13 (`latency-queue`): built, unit-tested, in part.** The face file is written after the reply, not before the state: `commitFace()` runs right after `onPublished` on the first frame, and the state carries `faceRevision` from the second poll (the lease, which releases the sound, is returned only after that write, so no sound starts without its face). The state and `reply.json` are NOT written together: `bridge/convai-continuous-speech.test.mjs` pins that a cancel or a failed state write never admits the reply, so they stay in sequence (one more atomic write, 2.5 ms idle). Measured with real atomic writes of a 90 KB face (240 frames of 61 values; medians of 40, two rounds): first frame to published 10.7 and 11.9 ms before, 5.5 and 5.8 ms after. The face write (5 to 6 ms idle) is the saving; the estimated 30 to 60 ms was under the running game.

`bridge/convai-continuous-speech.mjs`, `frame()`: on the first publish it writes the face file, then the state file, then
`reply.json`, each an atomic replace and each awaited (49 to 148 ms `firstPcm` to `published` in the records, of which the
`firstFrame` to `published` part is 30 to 102 ms). The game cannot use the face before it has the reply anyway. Proposal: on
the first publish, commit the state and `reply.json` together (`Promise.all`) and write the face file right after (the state
carries `faceRevision` only once the face file is written, which the game already handles). Saves about 30 to 60 ms per
continuous reply.

### 4.4 No fresh `speech-state.json` read on the critical path (voice path)

**Status 2026-10-13 (`latency-queue`): built, unit-tested.** `bridge/speech-state-cache.mjs`: a turn's questions (continuous available, face file mode, the `respond` gate, the voice-key check) read a copy at most 1 s old; receipts, the heartbeat watchdog and the speech slots keep fresh reads (a stale `slot` would risk overwriting the file that is playing). A failed read (`{}`, the game replaces the file by remove and rename) is never cached, and the last good copy answers for up to 5 s where the old code lost the voice. The 500 ms knowledge poll refreshes the copy, so there is no extra timer. Measured (a 2 KB file, 400 turns of three questions): 5.5 ms median per turn before, 0.011 ms after, idle and with four writers on the disk.

`respondStreamed` (`(await readSpeechState()).continuousAvailable`), `synthesizeReply` and `respond` (`audioReady`) each read and
parse `speech-state.json` during the turn (the Lua heartbeat rewrites it every few seconds). Proposal: a cached reader that
returns the last parse when it is under 1 s old (refreshed in the background by the existing 500 ms settings poll); the 5 s
freshness rule of `audioReady` is unchanged. Saves about 5 to 60 ms per streamed reply (a file read on a busy disk).

### 4.5 Keep the Mistral connection (text client)

**Status 2026-10-13 (`latency-queue`): built, unit-tested, live-measured on Mistral; not yet in the game.** `bridge/mistral-client.mjs`: the body is read to its end after `[DONE]` (bounded to 250 ms, then cancelled) and the cloud routes share a 60 s keep-alive agent (Node's own undici `Agent`, reached through the global dispatcher; `undici` is not a dependency). `warmConnection({provider})` (one unauthenticated `GET` of the provider origin, not a `HEAD`: Cloudflare answers `HEAD` with `Connection: close`) runs when the provider is applied and when the composer opens (`warmCloud` in `attachTextProvider`). Measured live, about 45 short Mistral requests: the old code already reused the connection at a 1.5 s gap (Mistral sends the last chunk and `[DONE]` in one read, so the abort was a no-op) but opened a new one every turn at an 8 s gap (Node's 4 s idle limit); the new code opened one connection and reused it at 8 s and 30 s gaps, and after the warm-up the first real request opened none. The saving is the connect cost, 36 to 48 ms (126 ms on a cold first lookup), on every turn that comes more than 4 s after the previous one; time to headers on the live runs (400 to 1000 ms) is server noise around it.

`bridge/mistral-client.mjs`: the stream is aborted at `[DONE]`, so Node's client never reuses the connection and every turn
pays DNS, TCP and TLS (36 to 60 ms, `docs/LATENCY_2026-10-12.md` section 5). Proposal: read the response to its end instead of
aborting (the body is a few bytes after `[DONE]`), and give the Mistral routes an `undici` `Agent` with `keepAliveTimeout` 60 s
(Node 20's default keeps 4 s). Saves about 55 ms per Mistral turn that comes within the keep-alive, plus the Voxtral calls on
the same host. Measure with `scripts/Measure-MistralCache.mjs`.

### 4.6 OmniVoice first phrase (voice path; from a helper's investigation)

**Status 2026-10-13 (`latency-queue`): item 1 built and unit-tested; item 2 deliberately not done; item 5 skipped.** Item 1: `prepareSpeech` (`bridge/speech-audio.mjs`) decodes, levels and writes the first phrase's WAV beside the slot files (`reply-pre-<id>.tmp`) while the face analysis runs in its worker (the analysis is started first, so the preparation's 10 ms of decoding does not delay it); `storeSpeech(..., {prepared})` only renames it into the slot `SpeechSlots` chooses under its lock (lease and cancel rules unchanged; an unused file is removed after a minute, at the next preparation and at start-up). The 40 KB `last-speech-timing.json` is written after the `reply.json` commit, not in front of it. Measured with the real functions on a 4.56 s phrase, analysis simulated as a 76 ms wait (medians of 30): analysis done to `reply.json` committed 112 to 90 ms idle, 110 to 83 ms with four writers on the disk, 284 to 257 ms with a 250 ms analysis; the store pipeline costs 17 ms idle here, so the live 363 ms (under the game) is where this pays more. Item 2 (a shorter first phrase) is not changed: its cost is a gap risk, not only prosody (phrase 2 renders while phrase 1 plays, and a 2 s first phrase gives it half the cover of a 4.5 s one), and neither that nor the prosody can be judged without OmniVoice running on the GPU and a listener; the knob is the `first` branch of `splitSpeechText` (min 6, target 12, max 22 words). Item 5 (provisional face, a Lua change) is not done.

Critical path today, all sequential: `synthesizeOmniPhrase` (`bridge/convai-bridge.mjs` about line 1101) awaits the synthesis,
then `jaliFace.analyseWav` (`bridge/jali-face.mjs`), then `publishResult` runs `stream.begin` / `slots.write` (reads
`speech-state.json`, levels and writes the WAV, builds the face timeline, writes `speech-stream.json`), a 40 KB diagnostic
`last-speech-timing.json` write, then `reply.json`. Ranked:

1. Start `slots.write` on the WAV while the analysis runs, and move the `last-speech-timing.json` write after the `reply.json`
   commit: about 150 to 300 ms of the 363 ms. Low risk (keep the slot lease and cancel order of `SpeechSlots`).
2. A shorter first phrase (6 to 8 words, the `first` branch of `splitSpeechText`, `bridge/speech-stream.mjs` about line 12):
   synthesis and analysis both scale with its length: about 0.4 to 1.0 s. Slightly choppier prosody on the first phrase.
3. Done in this pass: the convolution kernel in `bridge/jali-face-model.mjs` (was a scalar loop at about 0.55 GMAC/s) is a
   WebAssembly SIMD kernel, about 8 times faster on the whole analysis (section 1). Items 4 and 5 matter much less now.
4. Analysis of phrase 1 split over 2 to 4 workers with 0.9 s of overlap: 35 to 45 percent of the analysis offline.
5. The structural one: publish after about 1 s of audio-only rows with a provisional face and send the full face as a revised
   `chunk.face` in the manifest; Lua would need a one-shot `face.replaceTimeline` called from `refreshManifest` (75 ms cadence,
   no per-frame work). About 1.3 to 1.6 s. Highest risk (a Lua change, a pose pop when the face is replaced).

Check first on a live record: a one-phrase reply's `lipAnalysisMs` per second of audio against a multi-phrase reply's. If the
one-phrase figure is near the offline 0.17 s per second, phrase 2's synthesis is what slows the analysis.

### 4.7 Local AI (Local AI context agent)

### 4.8 Native (the native-core worktree, later)

**Status 2026-10-13: not done** (a plugin and Lua change for about 15 ms; the document itself says it is not worth the risk before the release).

- The plugin could expose `Io.Revision` for a set of channels in one call, or signal a reply by bumping a counter the Lua probe
  reads; the probe added here already costs only one call while a reply is due, so this is small.
- A native notification into Lua (a redscript callback the plugin calls when `reply.json` changes, observed by CET) would remove
  the 30 ms probe entirely: about 15 ms more per reply. Not worth the risk before the release.

## 5. The memory finding (not only latency)

The live log shows the embedding server never started in the game session (`[local:embed] embedding server did not start:
timeout`, then `memory extract failed (local-embed); retrying in 60 s`): the start timed out at 60 s. Offline it starts in 6.3
to 7.7 s (2.6 to 3.4 s with `-fit off`), on one thread at below-normal priority. Under the running game the CPU is busy enough
that one below-normal thread may not get the time to load the model in 60 s; that is unproven. So memory recall for the text
routes did not work in that session at all, and each turn paid 400 ms for it. After this pass a turn never waits for the start,
the start is lighter, and the server stays up 5 minutes once it is up. To check live: `[LocalAI]` lines in `bridge.stderr.log`
(no "did not start"), and `stages.steps` `transport` to `recalled` under 50 ms. If it still times out under the game, the next
step is two threads or normal priority for the start only (the server is idle between turns).

## 6. How it was measured

- Memory recall: `MemoryStore.retrieve` with the real `LlamaEmbedder` and the real b11560 server and granite model, one stored
  record, four turns 1.5 s and 4 s apart, old code (from `HEAD`) against new; script in the session scratchpad
  (`measure-recall.mjs`). Before: 404, 408, 26, 15 ms. After: 2, 1, 31, 29 ms (on both the server was up from turn 3; the
  change is that the two cold turns no longer wait).
- Embedding server start: `llama-server --embedding ... -t 1` raw, until `/health` answers, with and without `-fit off`, CPU
  and Vulkan builds: 4.5 to 7.7 s default, 2.1 to 3.4 s with `-fit off`.
- File detection: 40 atomic replaces (temp file and rename) of `last-input.json` at random times, detected by a 50 ms stat
  poll (mean 37.9 ms, median 45, max 63), a 150 ms poll (77.7, 77.3, 153) and `watchFiles` (7.9, 7.5, 15).
- Game reply leg: a simulation of the plugin worker's poll and Lua's frame-quantized check at 30, 60 and 90 FPS (20,000 replies
  each): 64 to 65 ms before (worker 30 ms, tick 0.1 s), 24 ms after (worker 15 ms, probe 30 ms). Not measured in the game.
- Lip-sync kernel: `JaliFace.analyse` on the 4.56 s `bridge/fixtures/local-stt-sample.wav` with the real model
  (`runtime/lipsync-model`), median of 9, old against new, and a 160 x 160 layer timed directly; `bridge/jali-face-kernel.test.mjs`
  compares the SIMD kernel with the scalar loop (the fixture models have no layer it takes).
- Unit tests: `bridge/memory-store.test.mjs`, `bridge/local-embed.test.mjs` (ready, warm, the retry rule, `-fit off`),
  `bridge/file-wake.test.mjs` (fake watcher and a real one on a temp folder), `bridge/native-core.test.mjs` (`revision()` and
  the two Lua probes).
- The muted headless harness (`scripts/Measure-TurnLatency.mjs`) does not include the memory store, the bridge's input poll or
  the game, so it cannot show these changes; it was not used for them.
