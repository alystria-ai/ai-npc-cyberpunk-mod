# Latency pass, 2026-10-12

From the player pressing Enter (or stopping talking) to the first sound, for every conversation route. This pass measured each stage,
found where a real turn lost 1.6 s, started the voice on the first sentence while the model is still writing, and made the Voxtral
reference upload smaller.

**Status: built and unit-tested; not yet run in the game.** The bridge that was running during the work was started before these
changes, and the game folder was not touched. The numbers marked "bridge" below come from the real bridge code (the real text host,
reply cleaning, voice delivery, renderer page in headless Edge and continuous speech) with simulated provider delays, see "How it was
measured". The numbers marked "measured" are real calls on 2026-10-12.

## What changed, in one list

| Change | Where | Saves |
|---|---|---|
| Every stage of a turn is time-stamped and written into `bridge-latency.json` (`stages`) | `bridge/turn-clock.mjs`, marks across the bridge | finding things; no time |
| The hidden browser and the local voice's renderer page are opened when a text route is warmed (composer open, look, nearby) and at bridge start | `RealtimeHost.prewarmLocal`, `LocalPcmHost.warm`, `attachTextProvider` | 0.2 s measured on an idle machine on the first voiced reply (the real turn lost up to 1.6 s there; section 2) |
| The voice starts on the first complete sentence while the model writes the rest (Mistral, Groq, local; Pocket and Voxtral; Omni gets its first phrase early) | `bridge/reply-stream.mjs`, `respondStreamed` in `convai-bridge.mjs`, `deliverPocketSpeech` | the time the model needs to finish after its first sentence: 0.17 to 0.45 s on Mistral and Groq, about 1.2 s on a local model |
| The Voxtral reference is sent as a 16 kHz clip cut to about 8 s (MP3 when ffmpeg is on the machine), prepared once and cached | `bridge/voxtral-reference.mjs`, `VoxtralVoice` `prepare` | 0.15 to 0.8 s of the first-audio wait, depending on the uplink |
| The turn's record updates before the model request are no longer awaited | `note()` in `convai-bridge.mjs` | one or two file replacements (5 to 60 ms each) |

The bridge's own work (prompt build, knowledge, reply cleaning, PCM hand-over, face and state writes, publishing) is under 100 ms in this
harness, no event-loop stall of 80 ms or more was seen in any of the 45 runs. The large items are the provider calls, so the wins come from
doing them earlier (streaming, warm-up) and sending less (reference).

## 1. The stages

`runtime/bridge-latency.json`, every turn, key `stages`: `marks` (milliseconds after the bridge read the request, so a mark that
happened earlier, such as the game writing the file, is negative), `order`, and `steps` (the wait from each mark to the next; they add
up to `totalMs`, so the record has no unexplained gap), plus `stalls` (any time the bridge's event loop was blocked for 80 ms or more,
checked every 25 ms for at most 20 s per turn and off between turns).

| Mark | Meaning |
|---|---|
| `inputWritten` | the game wrote the request file |
| `received` | the bridge read it (the origin) |
| `knowledge`, `admitted` | the turn's knowledge was prepared; memory admission and the receipt were recorded |
| `transport` | the reply was requested from the conversation route |
| `recalled`, `promptBuilt` | (text routes) memory recalled; the model's messages built |
| `llmSent`, `llmHeaders`, `firstToken` | the request left; the server answered; the first piece of text arrived |
| `firstSentence`, `fullText`, `replyReturned` | the first complete sentence is known; the model is done; the host handed the reply on |
| `voiceStart` | the bridge began to voice the reply (a streamed reply: its first sentence) |
| `browserReady`, `playStart`, `rendererReady` | the local voice's browser is running; its playback began; the renderer page is open |
| `ttsSent`, `firstPcm`, `firstPcmAccepted` | the voice was asked; its first audio arrived; the renderer accepted it |
| `firstFrame`, `published` | the first renderer state with audio reached the continuous speech; the reply was published to the game |
| `playbackObserved` | the renderer's clock showed sound playing |

The marks cost a map write each and reach the turn's clock through an `AsyncLocalStorage`, so no signature carries a clock around and a
mark made with no turn running does nothing. Lua is unchanged. The Convai route reports the marks that apply to it (`received`,
`knowledge`, `admitted`, `transport`, `firstPcmAccepted`, `firstFrame`, `published`, `playbackObserved`); its connection and
collection times stay in the old `timing` fields.

## 2. The missing 1.6 s

The real turn (typed, Local provider with Gemma 4 E4B, Voxtral voice, Alex, 2026-10-12 16:50):

| | ms after the request was read |
|---|---|
| transport requested | 162 |
| model done (162 + `llmMs` 1,797) | about 1,960 |
| **voice playback began** (end of audio, 10,961, minus the 7,425 ms of device drain that `LocalPcmHost` times from its start) | **about 3,540** |
| renderer accepted the first audio (+1,916 after the start) | 5,452 |
| published | 5,468 |

The voice itself took 1.9 s (reference upload and Voxtral) and the renderer accepted the audio 16 ms after the first packet, so the 1.6 s
sits between "the model is done" and "the voice begins". The only slow, awaited step there is `RealtimeHost.start()`, which
`playLocalPcm` runs before `LocalPcmHost.play` starts its clock: it launches the hidden Edge that renders the local voice. A text
route's warm-up never opened it (`warm` returned at once; only Convai connections opened pages), so the browser started on the first
voiced reply. The 507 ms `localPcmRendererReadyMs` in the same record is the page opening after that (a page that was already open
reports about 70 ms: bridge measurement below). This fits a first voiced reply after a bridge start, but it is **not proven**: the harness reproduces only about 0.2 s of it (below),
and the bridge's own log for that session was not available. The rest could be the browser starting slower under the running game, or
another awaited step in the real bridge that the harness does not have (the admission and receipt file reads). The new `browserReady`
and `playStart` marks name the step on the next live turn, and the stall record shows whether something blocked the loop.

Fix: `attachTextProvider.warm` now also calls `RealtimeHost.prewarmLocal()` (starts the browser, opens and keeps the renderer page;
never throws, never touches a running turn), and the bridge calls it once at start when a text route is active. The phone host is not
warmed (it has no voice). A renderer page that is being warmed is the page a turn starting meanwhile uses (no second page).

Measured here (harness, Edge cold against warm, idle machine, no game running): the browser start is 180 to 200 ms (`browserReady` minus
`replyReturned`, in all five routes) and the page opens in parallel with the first voice request; the first sound comes 220 to 240 ms
later when cold (Mistral + Voxtral 3,009 against 2,788 ms). A game using the CPU and disk makes the start longer; 1.5 s would be
seven times slower, which is possible but unmeasured.

## 3. Streaming the text into the voice

Convai already does this: its page streams the reply text and the audio, and `ConvaiContinuousSpeech` publishes on the first audio.
The text routes now do the same.

**The reply stream** (`bridge/reply-stream.mjs`). The text host feeds it the raw text as it arrives. It cleans the text the way a
finished reply is cleaned and watches for the first complete sentence. That sentence becomes the **head** when it is safe to speak:

- a whole sentence (a stop, question mark, exclamation mark or ellipsis, then a space and more text), at least 28 characters (a short
  "Hey." joins the next sentence) and at most 260;
- nothing the cleaning could still change: no bracket, brace, parenthesis, asterisk, underscore or angle bracket (voice and emotion
  tags, stage directions, markdown), and the reply does not open with a quotation mark;
- not out of character ("as an AI") and not a model's reasoning;
- "V." and "Mr." are told apart from a sentence end ("Hey V. Listen." is two sentences).

A reply with no such head is voiced after it is finished, exactly as before. Audio cannot be taken back, so a reply that steps out of
character after its head was spoken is **not asked again**: the head stands and the rest is dropped. The finished reply is made to
begin with the head (`reconcile`).

**The voice** (`deliverPocketSpeech`, `LocalPcmHost.play`, `PocketFacialStream`):

1. The renderer starts with the head as its text. Each clock snapshot carries the live text (`liveText`) and whether it is final, so
   the subtitles grow and the face model gets `setText(text, complete)`, as for Convai.
2. The head is synthesized and played at once. When the model is done, the rest (the tail) is synthesized into memory
   (`BufferedPcm`, concurrently with the head's audio), and its packets continue the head's numbering under the head's identity, so the
   renderer sees one utterance. A tail that cannot be voiced ends the reply on the head (`truncated`), the written reply stays complete.
3. If the model fails after the head, the head is the whole reply (spoken and shown).
4. The expression plan is made for the head, then once more from the finished reply (its emotion marks reach the planner through a
   live list); the mood is remembered and the receipt written once, from the whole.

**Which routes.** Mistral, Groq and the local AI, with the Pocket-engine voices (Pocket and Voxtral, including Voxtral's own fallback
to Pocket). **OmniVoice** renders one phrase at a time into a file, so it cannot take the tail the same way: when the head arrives,
the first phrase starts rendering while the model writes the rest, and is used if it is the phrase the finished reply starts with
(otherwise dropped). **Not streamed:** a reaction (a battle or loot line), a held look-ahead group speaker, the phone host, and the
microphone path (its time goes to speech recognition first; a follow-up could stream its reply the same way).

**Switch off:** `"replyStreaming": false` in `runtime/settings.json` (no menu entry), or `CYBERPUNK_CONVAI_REPLY_STREAM=0`.

**Cost of more requests.** A Voxtral reply is now up to two voice requests for the head and up to two for the tail, against up to two
before; they go through the shared Mistral scheduler (about one request a second, voice requests first).

## 4. The Voxtral reference upload

The reference clip is sent with every request. The one in the real turn was 557,718 bytes (the omni-long clip), 744 KB as base64. On
this machine's uplink the upload is most of Voxtral's first-audio wait: the same sentence, voice and code, six real calls
(`scripts/Test-VoxtralReferenceSize.mjs`, Judy, the 13.4 s omni-long clip; each variant twice for the two that were repeated):

| Reference | Body sent (base64) | Headers back | First audio | Whole reply |
|---|---|---|---|---|
| Original 24 kHz WAV, 13.4 s | 857 KB | 1,371 / 1,391 ms | 1,532 / 1,659 ms | 2,395 / 2,336 ms |
| Mono 16 kHz WAV, cut to 8.3 s | 354 KB | 943 / 1,328 ms | 1,227 / 1,631 ms | 2,074 / 2,513 ms |
| Mono MP3 64 kbit/s, cut to 8.3 s | 89 KB | 570 / 626 ms | 769 / 757 ms | 1,570 / 2,049 ms |

Does the clone stay the same? ECAPA speaker similarity of the output to the original reference was 0.50 and 0.65 for the full clip
(two calls of the same input differ that much), 0.58 and 0.57 for the cut 16 kHz clip, 0.58 and 0.51 for the cut MP3: inside the
call-to-call spread. The reference clips themselves score 0.99 to 1.0 against the original when only the format changes, and 0.91 to
0.93 when they are cut. **Please listen:** the outputs are in
`C:\Users\akshi\AppData\Local\Temp\claude\C--Users-akshi-Desktop-Code-Palace-Cyberpunk-Mod\e879aa3d-18fe-4a80-bd5a-b3a10be47999\scratchpad\voxtral-ref-size\` (a temporary folder; copy what you want to keep):
`judy-alvarez-A-original.wav`, `judy-alvarez-A2-original.wav` (the same input twice), `judy-alvarez-E-cut-16k-mono.wav`,
`judy-alvarez-E2-cut-16k-mono.wav`, `judy-alvarez-G-cut-mp3-64k.wav`, `judy-alvarez-G2-cut-mp3-64k.wav`; the references
themselves are `ref-A-original.wav` (642 KB), `ref-E-cut-16k-mono.wav` (265 KB), `ref-G-cut-mp3-64k.mp3` (67 KB).

**What ships** (`bridge/voxtral-reference.mjs`):

- `prepareReference` (pure JavaScript, no tool needed): mono, 16 kHz, cut to about 8.5 s at the quietest moment of the last 2.5 s (a
  pause, not a word) with a 5 ms fade; a clip already short is not cut. Checked against ffmpeg: within -53 dB.
- With ffmpeg on the machine (`ffmpeg` on the path or `CYBERPUNK_CONVAI_FFMPEG`), the same clip is also encoded as a 64 kbit/s MP3.
  Players without ffmpeg get the 16 kHz WAV. (Shipping pre-encoded MP3 clips would give every player the large saving: not done.)
- The result is kept on disk, `<references>/prepared/<voice>.wav|mp3` with a `.json` naming the source clip's hash and the settings, so
  the work is done once per character; a changed clip or setting is prepared again; a cache that cannot be written is ignored.
- The reference is prepared when the voice is warmed (`prepareProfile`), not on the first request. The first preparation costs about
  0.3 s of the bridge's time for one character.
- `timing.voiceReferenceBytes` now shows the size sent, with `voiceReferenceFormat`. `CYBERPUNK_CONVAI_VOXTRAL_FULL_REFERENCE=1` sends
  the whole clip as before.

## 5. The other waits, route by route

**Mistral and Groq** (12 real calls, `scripts/Measure-TextLatency.mjs`; the prompt was Judy's real one: 26,854 characters, about 5,930
tokens counted by the server):

- Mistral `ministral-8b-latest`, first token 430 ms when the prefix is cached (5,888 of 5,933 tokens), 750 to 960 ms when it is not.
  The cache is best effort: the same prefix and key seconds apart hit once and missed once. About 280 ms of the 430 is network and
  gateway. Cutting the world block to 40% saved 950 tokens, about 50 ms: persona and rules dominate, so the prompt was left alone.
- Groq `qwen/qwen3.8-27b`: first token about 620 ms, no prompt cache, server prefill about 415 ms for 6k tokens. The first sentence
  ends 20 to 30 ms after the first token, so streaming saves little there (15 to 80 ms).
- The first sentence ends 40 to 260 ms after the first token on Mistral, and the whole reply (76 to 202 characters) 350 to 450 ms
  later: that is what streaming recovers, more for longer replies.
- **Connections are not reused.** Every call opened a new connection (36 to 60 ms for DNS, TCP and TLS) because the stream is aborted
  at `[DONE]`. Draining it would let a later call reuse the connection, but only within the 4 s keep-alive of Node's built-in client,
  and the warm-up GET takes 340 to 710 ms itself. Saving about 40 to 65 ms a turn at most; not done.
- **Groq's free plan allows 8,000 tokens a minute.** One reply with this prompt leaves 1.2 to 1.9k, so a second Groq reply within
  about a minute is refused and the host falls back to Mistral. A longer persona would be refused outright. This is a limit of the
  plan, not of the code; a smaller Groq prompt would be needed to change it.
- Mistral's responses carry no rate-limit headers (the comment in `mistral-rate.mjs` says they do); Groq's do.

**Local AI.** `llama-server` runs with one slot, a 1 GiB host-memory prompt cache and 32 context checkpoints, and the prompt keeps the
persona, rules, format notes, world and summary before the changing right-now block, so most of a character's prompt is a cache hit
after the composer warm-up (`textHost.prewarm`). Not measured here: the GPU belongs to the game. The real turn took 1,797 ms for the
whole reply (memory retrieval up to 400 ms is inside that); with streaming the voice starts at the first sentence, about 1.1 s into
the turn in the bridge measurement.

**Voice first audio** (from the project's earlier measurements, not repeated while the game owned the GPU): Pocket first PCM 135 to
210 ms; OmniVoice 16 steps about 1.3 s short and 1.45 s long reference; Voxtral 0.75 s (small reference) to 1.6 s (large) on this
uplink, 2.1 s in the earlier probe.

**Convai.** Unchanged, apart from the marks. Its connection is warm after the composer opens (3 ms in the record above); the
remaining time is Convai's own.

## 6. How it was measured

- `scripts/Measure-TextLatency.mjs`: real Mistral and Groq calls with the real prompt (12 calls; keys read in memory from one line
  each, never printed). `--dry` builds the prompt and calls nothing.
- `scripts/Measure-TurnLatency.mjs`: one text-route turn through the real pieces, `node scripts/Measure-TurnLatency.mjs --runs 3`. Real:
  `TextProviderHost` (prompt, SSE client, reply cleaning), `ReplyStream`, `deliverPocketSpeech`, `LocalPcmHost`, the headless Edge
  renderer page with its audio worklet, `ConvaiContinuousSpeech` and the turn clock. Simulated: the model (a local SSE server with a
  first-token delay and a speed taken from the real calls above; the local model's shape is assumed to match the 1.8 s turn), the
  voice (a tone with a given first-audio delay and speed), and the game (a lease that always allows playback). "Published" is the
  moment the reply is written for the game; the game's own poll adds its usual few tens of milliseconds, and the renderer needs 400 ms
  of audio buffered before it makes sound (`playbackObserved` is the renderer's own clock moving). Medians of three runs. The renderer's browser is started muted (`--mute-audio`; the PCM path and the renderer's clock run the same), so a
  run is silent.
- Unit tests: `reply-stream`, `turn-clock`, `voxtral-reference`, and additions to `text-provider-host`, `pocket-speech`,
  `local-pcm-host`.
