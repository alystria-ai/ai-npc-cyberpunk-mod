# Automatic error reports

When the mod hits an error, it sends a small, redacted error report to the project's backend, so the developer sees the problem without asking players for logs. It is on by default. **Companion Manager > Settings > Privacy > Send error reports automatically** turns it off; then nothing is recorded or sent, and anything already waiting is deleted.

## For players

**What a report holds**

- What went wrong: the kind of error, its message and where in the code it happened.
- Versions: the mod's Scripts and Runtime, the game, Cyber Engine Tweaks, RED4ext, redscript, Codeware, ArchiveXL, Node and Windows. (Audioware and TweakXL are no requirements any more and are not collected.)
- Your choices: conversation provider, companion voice, Local AI model, interface language, and whether Mature content is on (on or off, nothing more).
- Your graphics card's name and memory, and how much RAM the PC has and how much memory Windows can hand out in all (RAM plus the paging file), two numbers.
- What kind of PC it is (`bridge/system-facts.mjs`; FPS first: it is saved in the state folder as `system-facts.json` and reused for 7 days, a PC with no fresh copy reads it again in the background, one PowerShell read at a time at idle priority, and a report never waits for it, so the very first report of an install may go out without these figures): the processor's name and its cores and threads; the Windows edition, build and display language; the security products Windows lists (such as Defender, on or off) and whether Smart App Control and Defender's Controlled Folder Access are on; whether the game's process runs as administrator; the game's drive (letter, fixed or removable, SSD or hard disk, free space, whether the game is under Program Files); the screen's size and refresh rate.
- The names of your installed mods, one level deep and never a path: the Cyber Engine Tweaks mod folders, the RED4ext plugin folders, the redscript folders and files, the `.archive` files, the REDmod folders, the tweak files and the plugin files next to the game. A long list is cut and says how many names were left out. This is what shows a conflict between mods.
- When replies stay slow: how long each stage of a few recent replies took (numbers and stage names only), their token counts and how long the session had run. Never what was said.
- The setup check's lines (the same ones as on the Help page).
- Up to 150 log lines from around the error: the conversation service's log, the launcher's, the mod's own logs, and the error lines of the redscript log.
- A random number for your installation, hashed twice, so reports from one computer can be counted together without identifying it.

**What it never holds:** API keys or tokens, what you or the characters say, typed lines, character memories, microphone audio, voice files, or your Windows user name. Every log line goes through the same redactor as the support report (keys, tokens, IDs and your account name are removed), and then through a second filter that removes anything that looks like conversation text. Your IP address is not stored: the backend keeps only a keyed hash of it, for at most two hours, to limit how often one address can send.

**How often:** at most one report per kind of error per day. A report that has to wait (the backend cannot be reached, or it asked the mod to wait) keeps the log lines of the moment the error was seen, already scrubbed, in its queue file, so it never sends a later session's log. Reports are sent in the background, a little after the error, never while a character is answering, and the mod never retries them in a loop.

**The notice.** The first time you load the game after updating, a notice says once that error reports are sent and where to turn them off. Nothing is sent before the game has shown it (reports queue locally until the notice is marked in `settings.json`), and a settings file that cannot be read is never read as an opt-in either: while it is unreadable the service records nothing, sends nothing and deletes nothing. The game then treats it like a fresh install (the setting is not saved off for it, so the player's other choice is not invented): the notice is shown and marked again, the queue is kept, and nothing is sent until that has happened.

**Where they go:** to the mod's own backend on Vercel (the same one that hands out the free tier's sign-in), stored for 30 days, readable only with the developer's admin secret.

The support report (**Settings > Help > Generate report**) says whether the setting is on, how many reports went out today and how many are waiting.

## How it works

```
 bridge (convai-bridge.mjs)        game Lua (mod/error-reports.lua)
   crash, failed turn, setup         service-silent, failed service,
   problem at start                  first-load setup check, versions
        |                                   |
        v                                   v
 <data>/error-reports/queue/<signature>.json     runtime/error-events.json
        \                                   /
         v                                 v
    supervisor (bridge-supervisor.mjs) + bridge/error-reports.mjs
      also: the service failed, the bridge exited, Lua errors in the mod's logs
        |
        v   one signed POST, 10 s timeout, off the turn path
    auth-backend  POST /api/errors/report  ->  Upstash Redis (30 days)
        |
        v
    scripts/Fetch-ErrorReports.mjs  ->  deliverables/error-reports/<signature>/<id>.json + INDEX.md
```

**Slow replies** (`bridge/slow-turns.mjs`, kind `slow-turn`). Players reported replies getting slower over a session (Local AI going from 2 to 3 s to a minute or two); the stage clock that already times every turn (`bridge/turn-clock.mjs`, `bridge-latency.json`) now also feeds a watch. When 3 of the last 5 turns took more than 10 s from the bridge reading the request to the first sound, or any one turn took more than 30 s (`SLOW_TURNS`), the bridge records one `slow-turn` event per run (`ErrorEvents.slowTurns`); the sender adds one report per kind per day and the Privacy setting. Left out of the trigger: a turn that failed (it is a `turn-failed`), a turn during which the game said it was paused or a menu was open (the game's playback lease carries `paused`, `onPaused` in `bridge/convai-continuous-speech.mjs`), and the first turn after Local AI loaded its model (slow by nature; it stays in the history). Whether the window is focused is not known to the bridge. The judging is a few array writes per finished turn, with no file read, no probe and nothing per frame or per audio chunk. The report's `slow` section (rebuilt field by field by `cleanSlow`, so no text can ride along): why it fired and the thresholds, turns this session and minutes since the start, provider and voice, the free video memory the Local AI saw at its last start (no new probe), the background connection counts, the sound times of the last turns, and for the first turns of the session and for the slow turns: the time of each stage (`marks`, milliseconds after the request), the model, the prompt tokens (new and cached, from the local model's trace) and the event-loop stalls. The signature is constant, so the backend takes it as it takes any other kind: no backend change was needed.

**Voice failures** (kind `voice-failed`; 2026-10-27). Every way a voice can fail to speak becomes a report, with a `voice` section (rebuilt field by field by `cleanVoice` in `bridge/error-events.mjs`, so only fixed words, numbers and a few scrubbed lines can ride along): the voice the player chose (`requested`), the one speaking when it failed (`active`), where replies go now (`fellBackTo`: another voice, `text` for subtitles only, `silent` for V's own line), whether playback was off, `cause` as one word (`windows-blocked`, `virtual-memory`, `no-cuda`, `out-of-memory`, `timeout`, `integrity`, `missing-files`, `no-audio`, `never-played`, `unknown`), the card vendors, its total memory and, on an NVIDIA card, its free memory read when the voice failed (`voiceHardware` in `bridge/convai-bridge.mjs`: the card list the bridge already caches and one `nvidia-smi` query, only for a failed voice), and the worker's last eight stderr lines (`tailLines`, `bridge/voice-failures.mjs`; they go through the report's redactor like every log line). The sources: a voice worker that did not start or died (`VoiceSelection.noteFailure`: OmniVoice, the Pocket voice, V's own Pocket worker; a worker with no CUDA is reported too now, an AMD or Intel card with OmniVoice chosen), and V's typed or spoken line that failed or finished without any sound (`v-line`, from the line's summary). The report's `choices` section already holds the voice settings, `system.gpu` the card names.

**The voice never played** (`bridge/voice-silence.mjs`, kind `voice-failed`, frame `voice-silence`). A voice that starts and then makes no sound fails nowhere, and the player sees subtitles only. A watch on the stage clock counts a reply as silent when playback is on, the voice planner gave the turn a voice, the reply was published, the turn did not fail, the game was not paused, and 30 s after the turn's run ended the renderer's clock had still not shown sound. After 3 silent replies with none that ever sounded in the bridge run, one report goes out with the counts, the furthest voice stage the last silent reply reached (`lastStage`: `ttsSent` means the voice was asked, `firstPcm` that audio came, `published` that the game was told) and the planner's reasons. Replies the planner keeps written on purpose (a language the chosen voice does not speak) are left out. One timer per unsounded turn, nothing per frame.

**Recording** (`bridge/error-events.mjs`, `mod/error-reports.lua`) only writes small files; nothing is sent from the bridge or the game.

- **Bridge crashes.** `installCrashCapture` listens on Node's `uncaughtExceptionMonitor`, which runs for an uncaught exception and for an unhandled rejection that ends the process, without changing how the process ends. It writes one queue file synchronously.
- **Failed turns.** After the failure reply is written, `ErrorEvents.turnFailed` records turns that failed for a reason that is not the player's own doing. Left out: a key the provider refused, a used-up plan or free limit, the daily allowance, the player's own custom endpoint or account (`custom-*`), a cancelled turn, the game ending a talk (`Continuous speech was stopped by the game`: V talked again, walked away or opened a menu; `Continuous speech game lease expired`: the game paused or was loading and stopped refreshing its permission; 4 of the first 16 reports), Local AI that is not installed, does not fit the graphics memory or needs Mature content, and microphone turns that failed for the device. Kept: timeouts, crashes, a Local AI server that never answers, refused requests, a backend that is down.
- **A Runtime with a file missing.** The bridge reads four data files before it answers anything (`RUNTIME_DATA_FILES`, `bridge/runtime-files.mjs`: the roster, the world knowledge, the phone contacts and the quest list). Before the first reports of 0.2.2 a Runtime extracted only partly made the bridge die on `ENOENT: no such file or directory, open ...` five times in a row (`bridge-rejection`, then `service-failed bridge-crashed`, which says nothing about the cause). Now the supervisor looks for the files before it starts the bridge and publishes `install-incomplete` (the game's "The Runtime is incomplete" line; the log names the missing files, never a folder), checking again every few seconds; a bridge that finds one missing itself ends with exit code 78 and one plain line, and the supervisor does not restart it. A file read that nobody waits for and that fails as the folder changes under it (`ENOENT`, `EPERM`, `EBUSY`, ...) no longer ends the bridge (`installFileErrorGuard`): it is logged, recorded once as `bridge-rejection`, and the service goes on. Every other unhandled rejection is still a crash. The same holds for the Node packages the bridge imports (`RUNTIME_PACKAGE_FILES`: `playwright`, `playwright-core` and one file deep inside it): second round of reports (2026-10-20), two more players whose bridge died at its first import on `Cannot find package 'playwright'` and on `Cannot find module './dispatchers/dispatcher'` inside playwright-core (a Runtime extracted only partly or cleaned by an antivirus). The supervisor now looks for those files too, and when a bridge still ends on Node's "Cannot find module/package" it reads that out of `bridge.stderr.log` (`missingModuleInLog`), logs one line naming the file relative to the Runtime, and publishes `install-incomplete` after the first start instead of five crashes (no `bridge-crash` report for it). Files of two versions side by side (Scripts 0.2.5 over a Runtime 0.2.2: the bridge ended at its first import six times) end on Node's `SyntaxError: The requested module '...' does not provide an export named '...'`; `missingModuleInLog` reads that as well, `versionMismatchInLog` tells it apart, and the supervisor logs `mismatchMessage` ("The Runtime does not match the mod's Scripts: ... Download the full Runtime again, or apply the Runtime update zips in order") and publishes `install-incomplete`; the game's line says the same (download it again, or apply the update zips in order).
- **A voice turn Convai did not answer (changed 2026-10-28, signature `cbb775b3`: "Convai did not finish the reply (transcript=true text=false ...)").** A microphone turn with a final transcript of more than three characters and no sign of a reply (no reply text, and Convai not reporting that it is thinking) for 15 s after the transcript last changed or Convai last thought no longer waits for the 60 s ceiling. `bridge/realtime-client.mjs` `collect` sends the same transcript once, as a typed line, to the same character (the poll that already runs while a turn waits; nothing for a reply that arrives in time or while Convai is working on one, and a normal reply takes a few seconds). The resend has 30 s for a reply of its own. Only when that passes too does the turn fail with the usual error and so the one report, whose detail now ends in `resent=true`. A transcript of one to three characters still ends as "No speech was heard" after 15 s, and a typed turn has no transcript to resend. If Convai answers both lines the first answer completes the turn.
- **A voice that could not start.** `ErrorEvents.voiceFailed` records `voice-failed` with `<engine>: <reason>` (`pocket`, `v-helper`, `omni`; the Pocket worker's own reason is in the message, for example the source check that failed), at most once per reason per bridge run. Added after the third round (2026-10-20): two players had no voice from V and the cause reached us only as log lines of an unrelated report.
- **Setup check.** The bridge's light check at start (version mismatch, packs one folder too deep, Local AI problems) and the game's first-load check (missing or old requirements, scripts that did not load). The game also writes the versions it knows (game, CET, Codeware), which every report of that session carries. A Scripts of one game with the Runtime of the other (6 installs on 27 Oct) shows as the setup line `build: problem runtime-wrong (scripts=2.5 runtime=2.31 game=2.5)`, a `setup-problem` event `build <code>`, and `scriptsGame` / `runtimeGame` in the report's `versions` (docs/GAME_VERSIONS.md, "Wrong build").
- **The service.** The supervisor records `service-failed` (with the supervisor's code, such as `bridge-crashed` or `browser-missing`) and a bridge that exited unexpectedly (`bridge-crash`, with the exit code; skipped when the bridge recorded its own exception just before). The game records `service-silent` (a service that never came up) and failures only it saw (the start script's `install-incomplete`, `game-folder-not-visible`).
- **A service that never started, and a sign-in that could not connect (added 2026-10-24).** The game's setup row `service never` carries a detail: `plugin-not-loaded` (this mod's RED4ext plugin, which holds the launcher, did not load: the Runtime is missing or not in place) or `no-launcher-trace` (the plugin loaded and still nothing reported); the setup line of every report of the session shows it too. The reporter drops that row when it is older than the supervisor that reads it (the service is running now, so the row is about an earlier game session; 6 of 12 installs sent it on the first day of 0.2.9 with the service up), and logs one line. A failed turn whose Convai sign-in could not reach the backend has `authCause` in its detail: one network code (`ENOTFOUND` DNS, `ECONNRESET` reset, `ETIMEDOUT` / `UND_ERR_CONNECT_TIMEOUT` connect timeout, `TimeoutError` our 25 s timer, a TLS or `CERT_` code, or `redirect`, `fetch-failed`, `unknown`) and never a host, address or message; the same code is in the bridge log line "Sign-in backend could not be reached (CODE); retrying". It is not part of the message, so the signature is one for every cause.
- **A bridge that ended without a word (added 2026-10-22, report 9ea03afb1e415236: exit code 4294967295, stderr stopping mid-turn, no JavaScript stack).** The supervisor now starts the bridge with Node's `--report-on-fatalerror --report-uncaught-exception --report-compact --report-directory=<data>/node-reports` (plus `--report-exclude-env` when its own Node knows it; the folder keeps the newest five reports and nothing older than two weeks). When the bridge exits unexpectedly the service log gets the exit code in words (0xC0000005 access violation, 0xC0000409 fast-fail, 0xC00000FD stack overflow, 0xFFFFFFFF "usually TerminateProcess by another program", 134 abort or out of memory; `bridge/bridge-diagnostics.mjs`), the last stage the bridge started and whether it announced its own exit, and a summary of Node's newest report (the error's first line, the top JavaScript frames and native symbols, heap and rss; never the environment, the command line or a folder). The stage comes from `<data>/bridge-stage.json` (`bridge/stage-marker.mjs`): the bridge notes the name of what it last started (`turn.<stage>` from the turn clock, `microphone.start|finish|cancel`, `vision.helper-start|capture`, `voice.worker-start`) in memory and rewrites a 300-byte file at most once a second, and only when the stage changed; the exit event writes `closed: true` and the exit code, so a file that is not closed means the process was ended from outside or died natively. The same facts ride on the `bridge-crash` report as `report.crash` (rebuilt field by field by `cleanCrash`, then redacted; the signature still uses only `exit code N`). The bridge also logs one `[Memory] rss ..., heap used of total (limit ...)` line every 5 minutes (this process only). The support report has `nodeReports` (up to three summaries) next to `runtimeFiles`.
- **Runtime files that are not ours (added 2026-10-22, reports c48505d9d69e7ad5 and 9ea03afb1e415236: "Fesir AI services ready: Cloud.ru + GigaAM" in the service log).** Every error report and the support report carry `runtimeFiles`: {state, checked, changed, extra, missing, names (at most five, "changed bridge/x.mjs")}, from `bridge/runtime-integrity.mjs`. A release ships `app/defaults/runtime-code-files.json` (written last by `build-release.mjs` from the bytes it packs: every .mjs/.cjs/.js/.py in `bridge/`, `launcher/` and `assets/` with the first 24 hex digits of its SHA-256; a Runtime update zip carries the new list because it differs at every release). It is worked out only when a report is built, one directory walk and one stat per file, and a file is read again only when its size or modification time changed since an earlier report in the same process. A Runtime from before 0.2.8 has no list and reports `no-list`.
- **Lua errors.** The supervisor reads the mod's two logs from where it last stopped, at most every five minutes: `AiNpcCyberpunkMod.log` (where Cyber Engine Tweaks writes a callback's uncaught error) and `runtime/probe.log` (the errors the mod caught and logged, `... failed: init.lua:150: attempt to index ...`). Lines from before the first look are never reported.

**Signatures.** `kind + normalised message + top frame` hashed to 16 hex characters. The message loses folders, IDs, long hex runs, numbers, long quoted text, case and spacing; the frame loses its line and column numbers. The same fault in another folder, after another delay or a few lines further down gives the same signature.

**Sending** (`bridge/error-reports.mjs`, run by the supervisor). The supervisor is a separate process for the whole game session: it outlives a crashed bridge and is never on a turn's path, so a report costs a turn nothing.

- A supervisor event is sent 15 s after it happens; everything else is looked at a minute after start and then every five minutes (one directory listing, two file sizes, one small JSON read).
- Throttles: one report per signature per installation per UTC day; the backend has its own per-install ceiling (`errorInstallPerDay` in `auth-backend/api/_lib/config.js`); a 10 s timeout per request; a failed send waits 15 minutes and five failures stop it for the session; a `404` (a backend without this endpoint) or `401` stops it for the session; a `429` waits as long as the backend says (five minutes to six hours) and then goes on; a `400` or `413` drops that report. Waiting reports keep for a week (the queue size is `QUEUE_MAX` in `bridge/error-events.mjs`). **The log excerpt of a waiting report** (added 2026-10-22): the reporter gives every queued record its log lines at its next look (a supervisor event at once, any other event within the five-minute look or the one a minute after start-up): the same sources, line counts and redactor as a sent report (`captureLogs`, `bridge/error-reports.mjs`), stored in the record's own file as `logs` (`attachLogs`, `bridge/error-events.mjs`). The record keeps the excerpt of the first time the error was seen (a repeat only raises the count). When it is sent the kept excerpt is checked and redacted again; a queue file from before this change has none and the log is read when it is sent, as before.
- State: `<data>/error-reports/sent.json` (the UTC day, today's count and signatures, the last send, the positions read in the Lua logs) and the queue folder beside it. One writer at a time.
- The address: `/api/errors/report` on the first backend address that comes with a secret, signed with that secret: (1) the sign-in backend's own settings, `url` and `secret` in `convai-auth.json` in the data folder (or `CYBERPUNK_CONVAI_AUTH_URL` and `CYBERPUNK_CONVAI_AUTH_SECRET`), backend mode need not be on: a developer's machine; (2) `app/defaults/error-reports.json` in the Runtime, `{"version": 1, "url": "https://<deployment>", "secret": "<CONVAI_AUTH_SIGNING_SECRET>"}`, written by the release build: a player's install. Only the url's origin is used. A second server (the Cloudflare Worker, `auth-backend-cf/`) can be named as `backupUrl` in `error-reports.json`, or in the sign-in settings of the data folder: a report the first server does not answer (the request fails, a server error, a block page) is sent to the second in the same flush, a failure counts only when both fail, and the server that answered stays first for the session; an answer (404, 401, 429) is obeyed, not taken to the other. `CYBERPUNK_CONVAI_ERRORS_URL` replaces the address. With neither, nothing is sent and events wait in the queue. The shipped secret is scrubbed from every report. Like the token endpoint's, it is obfuscation, not authentication: the limits are what bound abuse.

**The payload** (`buildErrorPayload`, at most 60 KB of JSON, far under 64 KB compressed):

```json
{
  "schema": 1, "install": "<32 hex: sha256 of the install id, salted>", "signature": "<16 hex>",
  "kind": "turn-failed", "message": "convai: Convai did not answer: timed out", "frame": "realtime-client.mjs:120 connect",
  "modVersion": "0.2.2", "count": 2,
  "report": {
    "source": "bridge", "firstAt": "...", "lastAt": "...", "sentAt": "...",
    "stack": ["realtime-client.mjs:120 connect", "..."], "detail": {"provider": "convai"},
    "versions": {"runtime": "0.2.2", "scripts": "0.2.2", "game": "2.31", "cet": "v1.35.0", "red4ext": "1.30.0", "codeware": "1.20.5", "...": "..."},
    "choices": {"provider": "convai", "effective": "convai", "voice": "pocket", "localModel": "auto", "matureContent": false, "language": "en"},
    "system": {"gpu": [{"name": "NVIDIA GeForce RTX 4070 Laptop GPU", "memoryMiB": 8188}]},
    "setup": ["versions: ok match", "game codeware: ok found"],
    "logs": [{"source": "bridge-stderr", "lines": ["..."]}, {"source": "service", "lines": ["..."]}],
    "privacy": {"redactions": {"secrets": 0, "ids": 3, "patterns": 1, "paths": 2}}
  }
}
```

`detail` holds only the keys of `DETAIL_KEYS` in `bridge/error-reports.mjs` (the provider and its error code, the Local AI reason, the voice `engine` and the voice worker's graphics memory `gpuDedicatedMiB` and `gpuSharedMiB`, and for a custom server's empty answer the `empty*` counts: how it ended the answer, the tokens it counted, the events, pieces and milliseconds, `emptyAnswerDetail` in `bridge/error-events.mjs`). Before 2026-10-22 the voice keys were recorded but dropped by this list, so every voice report had an empty `detail`.

Log sources and their share of the 150 lines: `bridge-stderr` 70 (the lines around the error's own message when it is found, else the end), `service` 20, `launcher` 10, `probe` 25 (around the error), `cet-mod` 15, `redscript` 10 (error lines only). Each line is cut to 300 characters.

Redaction, in order: the support report's `createRedactor` with every key file's value as a literal (`credentialSecrets`, `customServerSecrets`, `dataFolderSecrets` in `bridge/report-secrets.mjs`: the data folder's key files, the sign-in file's secret, the custom servers' keys, and the two secrets a Runtime ships: `app/defaults/convai-auth.json`, the sign-in request secret, and `app/defaults/error-reports.json`, the reports' own), then `withoutConversation` (quoted text of 12 characters or more with a space in it, and the values of `text=`, `reply:`, `prompt=`, `"text":`... fields), then the Windows account names this process can see (`USERNAME`, the profile folder, `os.userInfo()`). The `detail` object keeps only the fields the recorders write. `bridge/error-reports.test.mjs` runs the support report's planted secrets, IDs, account name and conversation text through the whole path and requires none of them to get out.

**Logs stay bounded.** The bridge's stdout and stderr (`bridge.stdout.log`, `bridge.stderr.log`) are rotated at each service start and, during a session, cut back by the supervisor to their last 3 MB when they pass 6 MB (checked every 5 minutes, `capLogFile`); the service log is cut to 500 KB at 1 MB. A poll of the bridge that keeps failing logs once per cause and then once a minute with a count (`pollLog`), never a line per tick. A queue file left half-written is removed after an hour.

**Cost.** Nothing per frame and nothing per turn: a failed turn pays one function call (the file write is deferred), the game writes its file once per distinct event of a session, and the supervisor's five-minute look is a few file reads in another process.

## Backend

`auth-backend/README.md`, "Error reports", has the endpoint, its limits, the storage layout, the admin calls and the estimate against the Upstash free tier. In short: `POST /api/errors/report` (signed like the token endpoint, 64 KB cap, one Redis script per report: per-address hourly and per-install daily limits, dedup per install and signature per UTC day, an index per signature with counts, versions and first and last seen, at most 10 bodies per signature, at most 300 bodies a day for the whole service, everything with a 30-day TTL); `GET`/`DELETE /api/admin/errors` with the admin secret.

## Reading the reports

```
node scripts/Fetch-ErrorReports.mjs
```

It reads the backend address from `runtime/convai-auth.json` and the admin secret from `runtime/convai-auth-admin.txt` (never printed), fetches every report it does not have yet into `deliverables/error-reports/<signature>/<id>.json` and writes `deliverables/error-reports/INDEX.md`, a table of every signature with its counts, versions and first and last seen (only fixed-shape fields; the message and frame go in fenced, escaped blocks under an untrusted-data header, and each saved report starts with an `_untrusted` notice), a line of totals by kind, and, for `slow-turn` reports, a table of first sound for the first turns against the slow ones. Options: `--url`, `--admin-secret-file`, `--out`, `--limit`, `--delete-fetched`.
