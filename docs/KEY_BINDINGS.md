# Key bindings

**Companion Manager > Key bindings** (a button on Home between **Character editor** and **Settings**, in Mod Configuration Menu and Native Settings UI alike). The mod's seven actions can be given a keyboard key or a controller button from inside the game, with no restart and no trip to Cyber Engine Tweaks (CET):

| Action | How the key acts | Runs |
|---|---|---|
| Talk by voice | hold it, speak, let go to send | `init.lua` `voiceKeyEdge('voice', false, down)` |
| Talk by text | tap it: the text box opens | `beginText(false)` |
| Group voice chat | hold it, speak, let go to send | `voiceKeyEdge('group_voice', true, down)` |
| Group text chat | tap it | `beginText(true)` |
| Talk to Johnny by voice | hold it, speak, let go to send (Johnny, wherever you face) | `voiceKeyEdge('johnny_voice', false, down, true)` |
| Talk to Johnny by text | tap it (Johnny, wherever you face) | `beginText(false, true)` |
| Companion Manager | tap it | `openManager()` |

A controller can talk by voice with a button of this page: give Talk by voice the left stick click (L3) or any other button (the **Controller talk button** setting of 0.3.1 to 0.3.3 was removed in 0.3.4, a saved one becomes L3 on Talk by voice). The keys set in CET's Bindings window are not shown on the page (the owner, 2026-10-25: no row for them); they keep working beside the keys set here.

The CET bindings (`registerHotkey` / `registerInput` in `init.lua`) are unchanged and keep working. Since 0.3.4 five actions have a key from the start: **F4** the Companion Manager, **F6** talk by text, **F7** talk by voice, **F8** group text chat and **F9** group voice chat (the two Talk to Johnny actions have none). The defaults are saved into `settings.keyBindings` once (`keyDefaultsGiven` marks a file that has been through it): an action that already has a key keeps it, a default whose key another action holds is skipped, and a key cleared later stays cleared. **Restore defaults** puts the five back. Vanilla clashes (`r6/config/inputUserMappings.xml` of game 2.5, checked 2026-10-28): **F9 is Quick load** (`QuickLoad_Button`), so holding it for group voice chat also asks the game for a quick load, and F4 is `SwitchFreeCamControl` (only while the free camera that F3 opens is active). F6, F7 and F8 are free.

The two **Talk to Johnny** actions (added 2026-10-25, `docs/TALK_FALLBACK.md`) are the last two slots (6 voice, 7 text) so the slots of an older list stay as they were; the list the redscript half gets carries them only when one of them has a key (otherwise it is the five-slot list it always was). The page shows them after Group text chat. The talk keys with nobody faced no longer reach Johnny: they go to the first member of the party (`docs/TALK_FALLBACK.md`), and these two keys are how Johnny is asked for. With Johnny in your head off, or before the story has him in V's head, a press shows a notice and starts nothing.

## What the player does

Each action has one button row (one look on the page; the hosts draw a read-only text row bigger and indented): **Key or button** shows the key set here, and pressing it starts the capture. Press **Key or button**, then the key or controller button. The line under **Back** says "Press the key or controller button for Talk by voice. Esc or B cancels." and the key's button reads **Cancel** meanwhile. The choice is saved at once ("Talk by voice is set to F7.") and works at once. **Clear** removes it. Esc (keyboard) or B (controller) cancels a Set; a Set nobody answers ends after 12 seconds; leaving the page drops it. A key another action of the mod already has is refused ("F7 is already used for Talk by voice. Choose another."). **Restore defaults** (NSUI's own button, the host's footer button in MCM) puts the default keys back and clears the others (the batch id is `keyBindings:reset`).

Choosable: letters, digits, F1 to F24, the arrows and navigation keys, the number pad, punctuation, Space, Enter, Tab, Backspace, Insert, Delete, Caps/Num/Scroll lock, Pause, Print screen, and the controller's A, B, X, Y, LB, RB, LT, RT, L3, R3, D-pad and View/Menu buttons (B cancels, so B itself cannot be bound). Not offered: Shift, Ctrl and Alt (they are how a shortcut is told from a key), the mouse, the sticks and Esc. The game still sees the key too: the page says to pick one the game does not use (the game's own action for a key is not taken away).

## How it works

- **Storage**: `settings.keyBindings` in `runtime/settings.json`, `{action = 'IK_F7'}` with the game's own name for the key (`EInputKey`). Default: the five keys above (`M.defaultKeyBindings()`). `mod/manager.lua` keeps only the seven actions, only names that look like a game key (`IK_...`), and no key twice (a hand-edited file is cleaned on load); `M.keyBindings()` reads it, `M.setKeyBinding(player, action, name)` writes one binding in one validated `applySettings` save, and `applySettings({keyBindings = {voice = false, ...}})` clears.
- **Listening**: `r6/scripts/CyberpunkConvai/KeyBinds.reds`, Codeware `Input/Key` callbacks (the same mechanism the manager popup and the phone already use; `PadTalk.reds` only hears the actions a button is mapped to, so it cannot hear an arbitrary key). The game calls the callback when a key goes down and when it comes up: nothing per frame, no timer, no polling. A callback with targets for the chosen keys is registered only while at least one binding is set; while a Set waits, a second callback is registered with a target for each key a player may choose and Escape (the list comes from Lua, `captureKeys`; no callback of the mod hears every key), and it is removed when the Set ends. A key pressed with Shift, Ctrl or Alt held is not a binding, a key repeat is not a second press, and the key that was just chosen is not pressed again until it has come up. Events of the bound keys go into a bounded queue (`d1`..`d5` down, `u1`..`u5` up) and `ConvaiKeyBindNotify` is called, which Lua observes (`Observe`), so a key is handled at the moment it happens; the 10 Hz tick drains the same queue if the observer could not be installed. The capture keeps to itself: its events (`kIK_F7`, a key during Set) go into a queue of their own that only the 10 Hz tick reads (`ConvaiKeyBindCaptureTake`), so saving the key, registering its binding and removing the capture callback all happen outside the game's key event, at most 0.1 s later (game 2.31 with Dark Future froze while a key was being set, 2026-10-25). The capture handler also caps itself: past 64 key events or 30 s it ignores every later event and queues `x`, and the tick then ends the Set as cancelled and removes the callback. Both handlers drop an event that arrives while one of them is running.
- **Deciding**: `mod/key-bindings.lua`, loaded by `init.lua` (`convaiKeyBindsModule`) only when a binding is saved or the page opens. It is ticked from the 10 Hz tick (`convaiKeyBindsTick`): with nothing saved and no Set in progress that is one table check. It registers the saved keys with the redscript half (the half reports what it holds, so a new player after a load gets them again) and runs the actions through the very functions the CET keys run. So the gating is the CET keys' own: `voiceKeyEdge` / `toggleVoice` / `beginText` refuse in menus, with the text box open, without a target, and so on, and `openManager` refuses where MCM would (V seated in a scene tier 3 gets the same notice). The one addition: nothing acts while V types in the phone's chat box (`ConvaiPhoneChatTyping`), where the keys reach the game too.
- **Hold and tap**: the voice actions use the CET key's own ids (`voice`, `group_voice`), so a CET key and an own key on the same action never start two recordings (`voiceKeyEdge` ignores the second down and the second up). The tap actions run when the key comes **up**, as a CET hotkey does (so the key's character is not typed into the box it opens).
- **One press runs once**: when the same key is bound in CET and here, both fire as it comes up, a few milliseconds apart. `convaiTapOnce(action)` (in the three CET hotkeys and in the module) lets the first through and drops the second within 0.4 s. With the module not loaded the CET hotkeys run as before.
- **Set**: `M.beginCapture` asks the redscript half to report the keys a player may choose (`ConvaiKeyBindsCapture(<list>)`; an empty list stops it) and waits; the tick reads what it heard. Escape and the controller's B cancel; a key that cannot be bound (a modifier, the mouse, a stick) is ignored and the Set goes on waiting; presses within 0.4 s of pressing Set are ignored (a held Enter repeating). The saved key is registered on the tick that reads it (with the capture still listening for its release until then), so the release of the key just chosen is heard, and the bound keys do nothing for half a second after a choice. The result comes back through `managerUi.keyBindResult`, which sets the line under **Back** and redraws the page.
- **Game versions**: the key target is the one place the builds differ. `GameVariant.reds` has `ConvaiKeyTarget(key, action)` (Codeware 2.31 filters by action; the 2.5 target does not) and now `ConvaiKeyTargetsByAction()` (true on 2.31, false on 2.5): `KeyBinds.reds` adds a press and a release target per key on 2.31, one target per key on 2.5, and checks the action in the handler on both. Both builds compile (`scripts/Compile-Redscript.ps1 -GameVersion 2.5` and `-GameVersion 2.31 -GameDirectory <the 2.31 folder>`), also against a game without Codeware (the methods that need it have plain stand-ins; the page then says "Key bindings need Codeware").

## Why a Set could do nothing (26 Oct triage, three installs)

The page is a menu, and a menu stops the game's clock: the frame delta is zero there, and the 10 Hz tick (`convaiKeyBindsTick`) is paced by that delta, so it does not run
while the page is open. Until 27 Oct a Set was read by that tick only: the key was heard, queued and never read, the 12 s timeout never came, and the log said
"waiting for a key" followed by "Set dropped" when the player left (installs `e940d8`, `72ad0d` of 0.3.1/0.3.2, four tries in 30 s on the second). The owner's own checks
passed because the shortcut that opens the manager from the world does not pause the game, and the tick ran. Now `mod/manager-ui.lua` `M.slowUpdate` (which runs in
menus, a quarter-second period) calls `mod/key-bindings.lua` `captureTick` while a Set waits: one global and one table read otherwise. `captureTick` ends the Set on its
12 s wall clock, reads the capture's queue and saves the key; the tick calls the same function for a Set made in the world, and a menu being open no longer throws the Set
away (only losing V does). At the main menu there is no V to hear a key: the button says "Load a save first. A key can be set only while a game is loaded." (before,
"The mod's scripts did not load"). A Set that ends with no key event heard at all (`ConvaiKeyBindCaptureHeard`, logged as "N key events heard") says "No key press reached the mod ... set the key in Cyber Engine Tweaks' Bindings";
that is the case to look for if Codeware's key callbacks do not arrive while a pause menu is open (not verified without the game).

## The Cyber Engine Tweaks line

CET stores a binding in `bin/x64/plugins/cyber_engine_tweaks/bindings.json` as one 64-bit number per action of a mod: four 16-bit slots of Windows virtual-key codes, the first key in the top 16 bits (F6 alone is `0x0075` followed by 48 zero bits; a chord such as Ctrl + J has the modifier first). The numbers exceed 2^53, so `mod/key-bindings.lua` (`decodeBind`, `decodeCet`) reads them as text and divides by 65536 four times. CET reads the file when the game starts and writes it when the game ends; **the mod never writes it**.

Two sources, in this order:

1. CET's own live answer, `IsBound(id)` and `GetBind(id)` (the calls the interface-language hints already use, `docs/COMPANION_HOTKEY_INPUT.md`): it shows a binding changed in CET's overlay this session at once, and is exactly CET's text ("F6", "Ctrl + J").
2. `bindings.json`, read through the CET sandbox's `io.open` (`../../bindings.json`, at most every 5 seconds), only when CET gives no such call. **CET's sandbox may refuse to open a file outside the mod's own folder**, in which case this source silently gives nothing; the decode is tested on the real file shape (`bridge/key-bindings.test.mjs`).

## Not verified without the game

If the gamepad does not arrive, a Set for a controller button simply keeps waiting and times out; keyboard keys are unaffected.
- That the key press reaches Codeware while the Companion Manager page is open (the Set), on both hosts.
- The CET line from the file (the sandbox question above).
